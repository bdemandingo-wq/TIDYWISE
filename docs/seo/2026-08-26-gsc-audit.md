## FINDING 1 — Duplicate `aggregateRating` on `/score/c/*` pages (Critical)

### Issue

The GSC "Review has multiple aggregate ratings" error affects 6 items — three score page URLs, each listed twice:

| URL | Business |
|---|---|
| `/score/c/canary-clean-atx-maids-fxeudk` | Canary Clean - ATX Maids |
| `/score/c/the-maids-in-austin-vx5dlm` | The Maids in Austin |
| `/score/c/austin-cleaning-service-k054uq` | Austin Cleaning Service |

**Root cause: prerender + runtime double injection.** The prerender system bakes one `<script type="application/ld+json">` with `LocalBusiness` + `aggregateRating` into the static HTML. Then when React hydrates, `ScoreCompanyPage.tsx` passes the same schema to `SEOHead`, and Helmet injects a **second** `<script type="application/ld+json">` into the DOM. Helmet does not deduplicate against pre-existing non-Helmet script tags.

Result: two JSON-LD blocks, each containing one `aggregateRating`, which Google reads as "multiple aggregate ratings." **503 score pages share this template** — only three are flagged because only three have been validated recently. The invalid count will keep climbing.

### Evidence

- `dist/score/c/canary-clean-atx-maids-fxeudk/index.html` — prerendered HTML contains exactly 1 `<script type="application/ld+json">` with 1 `aggregateRating` (injected by prerender at build time)
- `src/lib/routeMeta.ts:453-467` — `scoreCompanyRouteMeta()` builds `LocalBusiness` with `aggregateRating` from `google_rating` / `google_review_count`, returned as `jsonLd: [business]`
- `src/lib/prerender-routes.ts:194-204` — `patchHead()` takes `meta.jsonLd`, wraps in `@graph`, injects before `</head>`
- `src/pages/score/ScoreCompanyPage.tsx:221-255` — builds an identical `businessSchema` with `aggregateRating` (lines 246-254)
- `src/pages/score/ScoreCompanyPage.tsx:263` — passes `schemaJson={schemaJson}` to `<SEOHead>`
- `src/components/SEOHead.tsx:113-128` — SEOHead renders schemaJson via Helmet as a new `<script type="application/ld+json">`

### Impact
**P0.** Google discards the entire rich result. The invalid count will scale to all 503 score pages as Google re-validates.

### Fix
Remove `schemaJson` from the `<SEOHead>` call in `ScoreCompanyPage.tsx` (line 263). Let the prerendered JSON-LD be the single source. Prerender coverage is complete for all score companies (all are fetched and prerendered at build time). SPA navigation between score pages doesn't matter for Googlebot — it sees the initial HTML.

### Priority
**P0 — fix first.**

### Flagged: third-party rating data

The rating numbers come from `google_rating` and `google_review_count` in the `score_companies` table — data sourced from Google Places. Google's structured data policy is restrictive about republishing ratings aggregated from another platform: marking up review data you didn't collect is generally not permitted, and the rich result may not be granted even after fixing the duplication.

**Decision needed:** These are real Google review numbers, not fabricated. But they're republished, not originally collected. The score pages are a real asset. I'm flagging this for you to weigh — do not delete the ratings without your approval. The duplication fix (removing the double injection) is worth doing regardless.

### Separate: hardcoded self-serving ratings on marketing pages

`src/lib/seo/schemas.ts:9-15` defines `AGGREGATE_RATING` — hardcoded 4.9 / 138 reviews. Used on:
- `/` (landing) — `LocalBusiness` + `SoftwareApplication` = **two aggregateRating blocks on one page**
- `/contact` — `LocalBusiness`
- `/pricing` — `SoftwareApplication`
- All 9 `/features/*` pages — `SoftwareApplication`

These are self-serving (owner-provided, not from a third-party aggregator). Google prohibits this. The landing page's two blocks may also trigger the same GSC error once Google re-validates it. **Fix is deletion** — remove `AGGREGATE_RATING` and all references from marketing page schemas.

## FINDING 8 — Crawl Budget (94% JS, 3% HTML)

### Issue

Crawl stats show 94% JavaScript / 3% HTML requests from Googlebot. 10,981 total crawl requests against ~660 known pages.

### What the prerender system actually produces

- **815 prerendered HTML files** in `dist/`
- **354 JS chunks** in `dist/assets/`
- **2 CSS files**

Each prerendered HTML file contains correct `<title>`, `<meta>`, `<link rel="canonical">`, OG/Twitter tags, JSON-LD (where applicable), and a **hidden `<h1>`** inside `<div id="root">` — but **no visible body content**. The `<body>` is:

```html
<div id="root"><h1 style="position:absolute;left:-9999px;...">Page Title</h1></div>
```

Zero article text, zero internal links, zero visible content. Googlebot must execute all JS to see the page. This is a **meta-tag patcher, not a content renderer** — it does not use a headless browser.

Only 2 pages have `<noscript>` content: `/cleaning-business-software` (state grid) and `/contact`.

### Why the JS ratio is so high

This is explained by the combination of:
1. Empty prerendered bodies requiring full JS execution for every page (Finding 8)
2. Hundreds of `?claim=` URLs being crawled (Finding 9b)
3. 503 score pages, 80+ city pages, and 50+ state pages — all needing JS to render

### Cache headers
- `/assets/*` — `max-age=31536000, immutable` ✓
- `/index.html` — `no-store, no-cache` ✓
- **No cache headers for the 815 prerendered HTML files** — title/description updates may be served stale

### robots.txt
- Does not block JS/CSS ✓
- References sitemap ✓
- `/score/generate` is blocked despite having routeMeta and prerendered HTML — minor inconsistency

### Fix
1. **Short-term:** Add `<noscript>` blocks with key content and internal links to marketing pages
2. **Long-term:** Inject actual page content into prerendered HTML (hero text, article body, feature descriptions)
3. Add cache headers for prerendered HTML: `Cache-Control: public, max-age=3600`

### Priority
**P2** — prerender head tags work for indexing, but the empty body is the root cause of Findings 13, 15, and part of 16.

## FINDING 9 — "Alternate page with proper canonical tag"

### 9a. The apex redirect is partial — canonical doing the work

**Hypothesis confirmed:** The apex→www redirect only fires for paths the hosting layer recognises. No redirect configuration exists in this repo — no `_redirects`, `netlify.toml`, `vercel.json`, no edge function. The redirect lives entirely in Lovable Cloud hosting.

For paths that have a prerendered `dist/` file, the hosting serves that file (correct www canonical inside). For paths that DON'T match a prerendered file, the hosting falls through to the SPA shell (`dist/index.html`), which serves 200 with the homepage canonical (`https://www.jointidywise.com/`). **This is why hundreds of apex URLs show "alternate page with proper canonical" — the canonical is pointing to the www homepage, not to the matching www path.**

GSC evidence supports this: `https://jointidywise.com/pricing` redirects (it has a prerendered file), but apex URLs under `/score/c/`, `/blog/`, `/compare/`, `/features/` return 200 (they either lack prerendered files or the hosting treats them differently).

**This may share a root cause with the 403s in Finding 14** — if the hosting layer's route matching is path-dependent, both symptoms come from the same gap.

### Fix
**Lovable/hosting:** Configure a host-level 301 that matches on hostname alone (`jointidywise.com` → `www.jointidywise.com`), independent of path. The canonical tags are already correct in code — this is purely a hosting configuration.

### 9b. `?claim=` URLs consuming crawl budget — highest-leverage fix

**Source:** A single `<Link>` in `ScoreCompanyPage.tsx:407-411`:
```tsx
<Link to={`/login?claim=${encodeURIComponent(slug!)}`}>
  Already have an account? Log in to claim
</Link>
```

This renders as a followable `<a href>` with **no `rel="nofollow"`**. Every score page generates two crawlable URLs (`/login?claim=<slug>` and `/signup?claim=<slug>` via cross-links at `LoginPage.tsx:444` and `SignupPage.tsx:611`). With 503 score pages, that's ~1,006 additional crawlable URLs — all leading to auth pages that should not be indexed.

**robots.txt already disallows `?claim=`** (`public/robots.txt:54-56`):
```
Disallow: /*?claim=
Disallow: /*&claim=
```

But the links lack `rel="nofollow"`, so Googlebot discovers them before checking robots.txt. The disallow prevents indexing but NOT crawling — Googlebot still fetches them, executing JS each time.

**None of these URLs are in the sitemap.** ✓

**This is the highest-leverage fix in the entire audit.** Per Finding 16, real commercial pages sit in the "never crawled" queue because crawl budget is consumed by these claim URLs. Every crawl request reclaimed from `?claim=` is one that can reach a page that has never been seen.

### Fix
1. Add `rel="nofollow"` to the claim `<Link>` in `ScoreCompanyPage.tsx:407-411`
2. Add `rel="nofollow"` to cross-links in `LoginPage.tsx:444` and `SignupPage.tsx:611`
3. Combined with Finding 5's `noindex` on `/login` and `/signup`, this stops both discovery and indexing
4. The robots.txt disallow can stay as a belt-and-suspenders measure

### 9c. `?claim=` 404s — Googlebot-only, humans are fine

**The 404s in GSC are from the SPA routing, not from the application rejecting claims.** Here's the flow:

1. Googlebot hits `/login?claim=<slug>` and gets the prerendered `dist/login/index.html` — a **200 response**
2. The prerendered HTML has canonical `https://www.jointidywise.com/login` (correct, no query params)
3. If Googlebot executes JS, `LoginPage.tsx:33` reads the claim parameter and stores it
4. Claim validation only happens **server-side** after authentication, via `supabase/functions/score-claim-self/index.ts`

The edge function handles all cases properly:
- Valid claim: success (`score-claim-self/index.ts:56-70`)
- Already claimed by different user: 409 (`line 94`)
- Slug not found: 404 (`line 87`)
- Same user re-claiming: idempotent success (`line 100`)

## FINDING 15 — Programmatic Page Sets Crawled and Rejected

### Issue

### Prerender content analysis

**City pages (e.g., `dist/score/city/houston-tx/index.html`):**
- Correct title, meta description, canonical ✓
- Hidden H1 ✓
- **No JSON-LD**, no `<noscript>` body content, no visible content at all

- Correct title, meta description (unique per state — Illinois mentions Chicago) ✓

- **No JSON-LD**, no `<noscript>` body content, no visible content at all

- Note: parent `/cleaning-business-software` DOES get a `<noscript>` state grid via `buildStateGridNoscript()` at `prerender-routes.ts:104-113`. Individual state pages do not.

### Root cause

Google is choosing not to index because these pages are thin content. Raw HTML has:
1. Meta tags with city/state-specific strings
2. A hidden H1
3. Zero visible content

2. **Long-term:** Inject actual rendered content into prerendered HTML for all programmatic pages
3. **Honest assessment:** If these pages lack genuine per-location substance even after content injection (no local data, no named businesses, no pricing ranges), they may still not deserve to rank. More programmatic pages is not the remedy — richer content per page is.
