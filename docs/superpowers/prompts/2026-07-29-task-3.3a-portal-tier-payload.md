# Lovable prompt — Task 3.3a: portal payload gets `lifetime_spend` + derived tier

**Plan:** `docs/superpowers/plans/2026-07-29-loyalty-tiers-only.md` (Part 3, Task 3.3a)
**Status:** not yet run — queued behind Task 3.2 (landed)
**Target:** `supabase/functions/client-portal-api/index.ts` on the main project `slwfkaqczvwvvvavkgpr`

## Why this exists

Task 3.2 rewrote `LoyaltyTierBanner` to take `lifetimeSpend` + `tiers` and render nothing without them. Both inputs are currently unavailable from the portal, so **the banner is intentionally hidden until this ships**:

1. `client-portal-api` action `get_user_data` selects only `points, lifetime_points, tier` (`:199-202`) and returns no `lifetime_spend` (`:220-222`). The banner has no spend to compare against thresholds.
2. `loyalty_tier` is a **direct read of the frozen `customer_loyalty.tier` column** (`:222`). Task 3.1 corrected that column once, so it is right today — but it is no longer maintained, so it goes stale the moment an org edits its thresholds.

Hidden is better than the previous behaviour (every org saw TidyWise Cleaning's hardcoded ladder), but it is not the end state.

## The prompt

```
Please edit and deploy the edge function `client-portal-api` on the main project.
Two small changes, both inside the `get_user_data` case.

Context: customer_loyalty.tier is now FROZEN — no trigger maintains it. It was
corrected once on 2026-07-29 from resolve_customer_tier(), so it is currently
right, but it will go stale as soon as an org edits its client_tier_settings
thresholds. Tier is now a DERIVED value. Separately, the client portal needs
lifetime_spend to show tier progress, and the payload does not include it.

CHANGE 1 — add lifetime_spend to the loyalty select.

Currently:

  supabase
    .from("customer_loyalty")
    .select("points, lifetime_points, tier")
    .eq("customer_id", customer_id)
    .maybeSingle(),

Change the select to:

    .select("points, lifetime_points, tier, lifetime_spend")

CHANGE 2 — return a DERIVED tier, and expose lifetime_spend.

The response object currently ends with:

  loyalty_points: loyalty?.points ?? null,
  loyalty_lifetime_points: loyalty?.lifetime_points ?? null,
  loyalty_tier: loyalty?.tier ?? null,
  property_type: null,

Replace loyalty_tier with a call to the resolver, and add loyalty_lifetime_spend:

  - Call: supabase.rpc("resolve_customer_tier", { p_customer_id: customer_id })
    This function is SECURITY DEFINER and allows the service_role path, which is
    what this function uses, so no grant change is needed.

  - loyalty_tier must be the resolver's return value. The resolver returns NULL
    when the customer's lifetime_spend is below that org's LOWEST min_spending —
    not every org starts a tier at $0. Pass that NULL straight through. Do NOT
    substitute 'bronze', 'none', or the frozen column value: the portal renders
    nothing for a null tier, which is correct, and a fallback would silently
    promote a customer who has not reached the org's first tier.

  - IMPORTANT on failure handling: if the RPC errors, return an ERROR from this
    action — do not fall back to loyalty?.tier and do not silently send null.
    A stale-but-plausible tier and a silently-missing tier are both worse than a
    visible failure here, because the customer cannot tell either from a bug.
    Use the same err(...) helper the other cases in this function use.

  - Add: loyalty_lifetime_spend: loyalty?.lifetime_spend ?? null

  Keep loyalty_points and loyalty_lifetime_points exactly as they are — they are
  still read by the portal's loyalty card.

Do NOT change any other action in this function. Do NOT change the
customer_loyalty table. Do NOT write to customer_loyalty.tier anywhere — it is
frozen deliberately.

Please confirm the function is DEPLOYED, not just committed — a commit does not
deploy an edge function in this project.
```

1. **`ClientPortalContext.tsx`** — add `lifetime_spend: number | null` to the `LoyaltyInfo` interface (`:32-36`) and map `lifetime_spend: row.loyalty_lifetime_spend` at both mapping sites (`:143`, `:375`).
