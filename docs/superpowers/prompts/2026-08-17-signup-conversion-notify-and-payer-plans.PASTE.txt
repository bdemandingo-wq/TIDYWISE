=== FIX 1b — A SECOND NOTIFICATION WHEN A TRIAL CONVERTS ===

Nothing currently tells you when someone starts paying. Add it to
supabase/functions/stripe-subscription-webhook/index.ts, which already handles
customer.subscription.updated and already resolves the organization.

Detect the trial-to-paid transition. On an updated event Stripe includes
event.data.previous_attributes; the transition is previous status 'trialing'
and current status 'active':

    const previousStatus =
      (event.data.previous_attributes as { status?: string } | undefined)?.status;
    const converted = previousStatus === "trialing" && sub.status === "active";

Read the plan and the price OFF THE SUBSCRIPTION OBJECT. Do not import
ChoosePlanPage's constants and do not hardcode amounts — two price lists drift,
and the one on this side would be the one nobody notices is wrong:

    const item = sub.items.data[0];
    const price = item?.price;
    const amount =
      typeof price?.unit_amount === "number"
        ? `${(price.unit_amount / 100).toFixed(2)} ${String(price.currency).toUpperCase()}`
        : "unknown amount";
    const interval = price?.recurring?.interval ?? "unknown interval";

    // create-subscription stamps tidywise_plan on the subscription's metadata.
    // Fall back to the price nickname rather than to a plan-name table.
    const planName =
      (sub.metadata as Record<string, string> | undefined)?.tidywise_plan ??
      price?.nickname ??
      "unknown plan";

Send it the same way the signup notification does — an SMS through OpenPhone,
to the same platform-admin number, using the same org SMS settings lookup.
Do NOT invent an email path; a second channel is a second thing to maintain.

Message body:

    `TidyWise: trial converted to paid\n` +
    `Org: ${organizationName}\n` +
    `Plan: ${planName}\n` +
    `Price: ${amount} / ${interval}\n` +
    `Subscription: ${sub.id}`

Fire it only when `converted` is true, and make it non-fatal: wrap the send in
try/catch and log failures. A notification that fails must never roll back or
block the plan_tier sync that this webhook exists to perform.

Do not change updateOrgPlanTier, subscriptionToPlanTier, the tier resolution,
or the created/deleted branches.


=== FIX 2 — "WHO'S PAYING" READS 0 FOR EVERY PLAN ===

src/hooks/useBillingRevenue.ts, inside useBillingPlanPayers, resolves plan_type
with a client-side join:

    supabase.from('organizations').select('id, plan_type').in('id', orgIds)

organizations has exactly one SELECT policy — owner_id = auth.uid() OR
is_org_member(id) — and no platform-admin bypass. So that call returns only
orgs the viewer personally belongs to: one, for either platform admin. And that
one org is excluded from this table by design, so ZERO plan types resolve and
all 14 payers land in "Other — unrecognised plan". Server-side the data is
correct: lifetime 12, pro 1, basic 1.

The join is not wrong, its route is. Give it a path that is not RLS-limited.

2a. MIGRATION — a gated resolver, same shape as broadcast_audience:

  create or replace function public.billing_payer_plan_types(p_org_ids uuid[])
  returns table (organization_id uuid, plan_type text)
  language sql
  stable
  security definer
  set search_path = public
  as $$
    -- SECURITY DEFINER because organizations' RLS has no platform-admin
    -- bypass, which is the whole bug. It therefore authorizes the caller
    -- itself: a non-platform-admin gets zero rows, not a cross-tenant read of
    -- who pays for TidyWise.
    select o.id, o.plan_type
    from public.organizations o
    where o.id = any(p_org_ids)
      and public.is_platform_admin();
  $$;

  revoke all on function public.billing_payer_plan_types(uuid[]) from public, anon;
  grant execute on function public.billing_payer_plan_types(uuid[]) to authenticated;

2b. HOOK — call it instead of the table.

Replace the organizations lookup inside useBillingPlanPayers with:

      const { data: orgs, error: orgError } = await supabase
        .rpc('billing_payer_plan_types', { p_org_ids: orgIds });
      if (orgError) throw orgError;
      for (const o of orgs ?? []) {
        planTypes.set(o.organization_id as string, (o.plan_type as string) ?? null);
      }

Note the key is organization_id, not id — the RPC returns the column under that
name. Everything else in the hook stays: the orgIds collection, the throw on
error, the plain-object return. Do not widen billing_plan_payers itself; that
view is the ledger and should not learn about access tiers.
