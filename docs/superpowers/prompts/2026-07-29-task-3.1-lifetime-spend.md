# Lovable prompt — Task 3.1: `lifetime_spend`, tier correction, derived tier

**Plan:** `docs/superpowers/plans/2026-07-29-loyalty-tiers-only.md` (Part 3, Task 3.1)
**Status:** not yet run
**Target:** main Supabase project `slwfkaqczvwvvvavkgpr` (Lovable Cloud — must be run by Lovable in-chat; the CLI and external MCP cannot reach it)

Two design decisions embedded below, recorded here so they are not re-litigated:

1. **The stored `tier` is corrected once, then frozen.** If we simply stop writing it, the portal keeps reading known-wrong strings (`ClientPortalContext.tsx:143`, `:375`) until Task 3.3 switches readers to the resolver. Correcting once means the transitional window shows the right answer. It can go stale if an org edits thresholds before 3.3 lands — bounded and documented.
2. **A per-booking idempotency guard is added.** Because `lifetime_spend` never decrements, an admin un-completing and re-completing a booking would otherwise count it twice, with no way to take it back.

## The prompt

```
Please run a migration on the main project (slwfkaqczvwvvvavkgpr). This is a
DATA CORRECTION, not just a schema change — see section 2. Run it in one
transaction and report the numbers in section 5 at the end.

Background you need, because it explains why the backfill matters:

  award_loyalty_points is currently `AFTER UPDATE ON public.bookings`. But
  process-migration-import inserts bookings already mapped to
  status='completed'. An INSERT never fires an UPDATE trigger, so every
  migrated historical booking awarded ZERO loyalty points. Customers who came
  in through a data migration are sitting at the wrong tier today — a customer
  with $6,000 of imported history shows lifetime_points = 0 and reads as the
  lowest tier.

  Separately, tiers are defined PER ORG in client_tier_settings, keyed on
  min_spending / max_spending in DOLLARS. 29 orgs have set those deliberately.
  But customer_loyalty.tier is written from hardcoded point thresholds
  (500/2000/5000) in two places, both ignoring client_tier_settings. So the
  stored tier is wrong for those orgs.

  Confirmed: no org has overlapping min_spending/max_spending ranges, so
  "highest tier_order wins" is a safe tie-break.

==================================================================
SECTION 1 — MEASUREMENT TABLE + BEFORE SNAPSHOT
==================================================================

Capture the "before" state into a table so it survives this chat.

CREATE TABLE IF NOT EXISTS public.loyalty_tier_correction_audit (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  phase text NOT NULL,                    -- 'before' | 'after'
  customer_id uuid NOT NULL,
  organization_id uuid,
  completed_spend numeric(12,2),
  stored_tier text,
  correct_tier text,
  captured_at timestamptz NOT NULL DEFAULT now()
);

INSERT INTO public.loyalty_tier_correction_audit
  (phase, customer_id, organization_id, completed_spend, stored_tier, correct_tier)
SELECT 'before',
       c.id,
       c.organization_id,
       COALESCE(s.spend, 0),
       cl.tier,
       (SELECT cts.tier_name
          FROM public.client_tier_settings cts
         WHERE cts.organization_id = c.organization_id
           AND COALESCE(s.spend,0) >= cts.min_spending
           AND (cts.max_spending IS NULL OR COALESCE(s.spend,0) <= cts.max_spending)
         ORDER BY cts.tier_order DESC
         LIMIT 1)
FROM public.customers c
JOIN public.customer_loyalty cl ON cl.customer_id = c.id
LEFT JOIN (
  SELECT customer_id, sum(total_amount) AS spend
  FROM public.bookings
  WHERE status = 'completed' AND customer_id IS NOT NULL
  GROUP BY customer_id
) s ON s.customer_id = c.id;

Note: correct_tier is NULL for two different reasons — the org has no
client_tier_settings rows at all, or the customer's spend is below that org's
lowest min_spending. Both are legitimate. Only compare where correct_tier IS
NOT NULL.

==================================================================
SECTION 2 — THE COLUMN AND THE BACKFILL (the correction)
==================================================================

ALTER TABLE public.customer_loyalty
  ADD COLUMN IF NOT EXISTS lifetime_spend numeric(12,2) NOT NULL DEFAULT 0;

COMMENT ON COLUMN public.customer_loyalty.lifetime_spend IS
  'Monotonic lifetime spend in dollars, accumulated from completed bookings.
   INCREMENT-ONLY — never decrement on any path. Refunds, post-completion
   charge edits, and status reversals must not reduce it: a refund must not
   demote a customer. Backfilled 2026-07-29 from sum(bookings.total_amount)
   where status=completed. Baseline is "spend as currently recorded", not "as
   originally charged" — edit history is not retained. This is the tier basis,
   compared against client_tier_settings.min_spending.';

Backfill existing loyalty rows:

UPDATE public.customer_loyalty cl
SET lifetime_spend = COALESCE(b.spend, 0),
    updated_at = now()
FROM (
  SELECT customer_id, sum(total_amount) AS spend
  FROM public.bookings
  WHERE status = 'completed' AND customer_id IS NOT NULL
  GROUP BY customer_id
) b
WHERE b.customer_id = cl.customer_id;

Create loyalty rows for customers who have completed bookings but no
customer_loyalty row at all (another consequence of the INSERT gap):

INSERT INTO public.customer_loyalty
  (customer_id, organization_id, points, lifetime_points, lifetime_spend)
SELECT b.customer_id,
       min(b.organization_id),
       0, 0,
       sum(b.total_amount)
FROM public.bookings b
WHERE b.status = 'completed'
  AND b.customer_id IS NOT NULL
  AND NOT EXISTS (
    SELECT 1 FROM public.customer_loyalty cl WHERE cl.customer_id = b.customer_id
  )
GROUP BY b.customer_id;

==================================================================
SECTION 3 — THE TWO RESOLVER FUNCTIONS
==================================================================

Both SECURITY DEFINER with `SET search_path = public`. SECURITY DEFINER
bypasses RLS, so each MUST authorize the caller internally — do not grant
either to `authenticated` without that check.

(a) get_org_tiers(p_organization_id uuid)
    RETURNS TABLE (tier_name text, tier_order integer, min_spending numeric,
                   max_spending numeric, benefits jsonb, color text)

    - Same body and the SAME four-tier default fallback as the existing
      get_loyalty_tier_info. Reuse that logic; do not invent new defaults.
    - Caller check: allow if session is service_role, OR
      is_org_member(p_organization_id). Fail closed on any error resolving
      membership.
    - REVOKE ALL FROM PUBLIC, anon.
      GRANT EXECUTE TO authenticated, service_role.
      (Safe to grant to authenticated because it authorizes internally.)

(b) resolve_customer_tier(p_customer_id uuid) RETURNS text

    - Resolve organization_id from public.customers for that customer.
    - Read customer_loyalty.lifetime_spend.
    - Return the tier_name from client_tier_settings where
        lifetime_spend >= min_spending
        AND (max_spending IS NULL OR lifetime_spend <= max_spending)
      ordered by tier_order DESC, limit 1.
    - CRITICAL: return NULL when lifetime_spend is below that org's LOWEST
      min_spending. NOT every org starts a tier at $0. Do NOT fall back to the
      lowest tier — that would silently promote a customer who has not reached
      it. NULL means "no tier yet" and the UI renders nothing.
    - If the org has no client_tier_settings rows, apply the same default
      fallback as get_org_tiers.
    - Caller check: service_role, OR is_org_member(that customer's org).
    - REVOKE ALL FROM PUBLIC, anon.
      GRANT EXECUTE TO authenticated, service_role.

==================================================================
SECTION 4 — WIDEN THE TRIGGER, MAINTAIN lifetime_spend, STOP WRITING tier
==================================================================

Replace award_loyalty_points and its trigger:

  - Trigger becomes: AFTER INSERT OR UPDATE ON public.bookings FOR EACH ROW

  - Award when the row is NEWLY completed:
      (TG_OP = 'INSERT' AND NEW.status = 'completed')
      OR (TG_OP = 'UPDATE' AND NEW.status = 'completed'
          AND OLD.status IS DISTINCT FROM 'completed')
    Use IS DISTINCT FROM so a NULL OLD.status behaves correctly.

  - IDEMPOTENCY GUARD (new — please add this): before awarding, skip if this
    booking has already been credited. Check for an existing
    loyalty_transactions row for NEW.id (booking_id) with the earning
    transaction_type this codebase already uses — match the existing
    convention rather than introducing a new value.
    Why: lifetime_spend is increment-only, so without this guard an admin
    un-completing and re-completing a booking would count it twice, and the
    monotonic rule means we can never take it back.

  - On award:
      points          += FLOOR(NEW.total_amount)   (unchanged, 1 pt per dollar)
      lifetime_points += FLOOR(NEW.total_amount)   (unchanged)
      lifetime_spend  += NEW.total_amount          (NEW — full precision, not floored)
    Create the customer_loyalty row if absent, as it does today.

  - STOP writing customer_loyalty.tier. Remove the hardcoded 5000/2000/500
    tier logic entirely. Do NOT drop the tier column — other code still
    selects it.

Then correct the stored tier ONCE, so it is right at the moment we stop
maintaining it (otherwise the portal keeps reading stale wrong values until
the frontend switches to the resolver):

UPDATE public.customer_loyalty cl
SET tier = public.resolve_customer_tier(cl.customer_id),
    updated_at = now();

COMMENT ON COLUMN public.customer_loyalty.tier IS
  'FROZEN 2026-07-29. No longer maintained by any trigger. Corrected once from
   resolve_customer_tier() at that date. Tier is now DERIVED — call
   resolve_customer_tier(customer_id) or get_org_tiers(organization_id). This
   column is a transitional snapshot and will go stale if an org edits its
   thresholds. Do not write to it.';

==================================================================
SECTION 5 — AFTER SNAPSHOT + THE NUMBERS I WANT
==================================================================

INSERT INTO public.loyalty_tier_correction_audit
  (phase, customer_id, organization_id, completed_spend, stored_tier, correct_tier)
SELECT 'after', cl.customer_id, cl.organization_id, cl.lifetime_spend,
       cl.tier, public.resolve_customer_tier(cl.customer_id)
FROM public.customer_loyalty cl;

Then please paste all five of these result sets:

-- A. Headline: how many people were at the wrong tier, and are now correct
SELECT
  count(*) FILTER (WHERE phase='before' AND correct_tier IS NOT NULL
                     AND stored_tier IS DISTINCT FROM correct_tier) AS wrong_tier_before,
  count(*) FILTER (WHERE phase='after'  AND correct_tier IS NOT NULL
                     AND stored_tier IS DISTINCT FROM correct_tier) AS wrong_tier_after
FROM public.loyalty_tier_correction_audit;

-- B. The migration gap specifically: real spend, zero points
SELECT count(*) AS customers_with_spend_but_no_points,
       round(sum(cl.lifetime_spend), 2) AS invisible_spend_dollars
FROM public.customer_loyalty cl
WHERE cl.lifetime_spend > 0 AND COALESCE(cl.lifetime_points, 0) = 0;

-- C. Which businesses were affected, worst first
SELECT o.name AS organization,
       count(*) AS customers_corrected
FROM public.loyalty_tier_correction_audit a
JOIN public.organizations o ON o.id = a.organization_id
WHERE a.phase='before' AND a.correct_tier IS NOT NULL
  AND a.stored_tier IS DISTINCT FROM a.correct_tier
GROUP BY o.name
ORDER BY customers_corrected DESC;

-- D. What the corrections actually looked like
SELECT COALESCE(stored_tier,'(none)') AS was,
       COALESCE(correct_tier,'(none)') AS now,
       count(*) AS customers
FROM public.loyalty_tier_correction_audit
WHERE phase='before' AND correct_tier IS NOT NULL
  AND stored_tier IS DISTINCT FROM correct_tier
GROUP BY 1,2
ORDER BY customers DESC;

-- E. Sanity: nothing decrements lifetime_spend anywhere
SELECT count(*) AS decrementing_functions
FROM pg_proc
WHERE prosrc ILIKE '%lifetime_spend%'
  AND (prosrc ILIKE '%lifetime_spend =%-%' OR prosrc ILIKE '%lifetime_spend - %');

Expected: A.wrong_tier_after = 0. E = 0. B is the migration gap — that number
is how many customers had spend the loyalty system could not see.

Do NOT change client_tier_settings. Do NOT alter min_spending or max_spending —
29 orgs set those deliberately and there is no conversion happening here.

Confirm the migration RAN, not just that a file was created.
```

## Checking the result

**A. `wrong_tier_after` must be 0.** If not, `resolve_customer_tier` and the one-time `tier` correction disagree — the resolver is non-deterministic. Stop before touching the frontend.

**B is the headline number** — customers with real completed spend the loyalty system could not see, plus the dollar total that was invisible.

**E must be 0**, proving monotonicity is structural rather than a convention someone can breach later.
