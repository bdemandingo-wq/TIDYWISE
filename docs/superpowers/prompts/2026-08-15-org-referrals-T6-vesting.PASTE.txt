=== WHAT THIS DOES ===

Counts the referred org's successful payments and vests the referrer's free
month on the SECOND one. This is the whole anti-abuse design: of the 13
subscriptions in the only cohort old enough to have completed, 3 (23%) never
reached a second payment. Vesting on the first payment would pay out on every
one of those.

Nothing here grants anything. It marks the referral 'qualified' and calls
`grant-referral-reward`, which is Task 7.

=== COUNT ABSOLUTELY, DO NOT INCREMENT ===

This is a correction to the plan, which said "increment
referred_paid_invoice_count". THAT IS WRONG and must not be implemented.

Stripe explicitly may deliver the same webhook more than once. An increment
would over-count on a redelivery and vest the reward early — on what is really
the first payment. It would also never recover from a missed delivery.

Instead, ASK STRIPE for the absolute count each time:

```ts
const paidInvoices = await stripe.invoices.list({
  subscription: inv.subscription as string,
  status: "paid",
  limit: 100,
});
const paidCount = paidInvoices.data.filter((i) => (i.amount_paid ?? 0) > 0).length;
```

Then WRITE that number, never `count + 1`. Idempotent by construction, and it
self-heals if a webhook was ever missed.

NOTE `amount_paid > 0`, not `billing_reason`. With the 14-day trial Stripe
issues a $0 invoice at subscription creation, so `billing_reason ===
'subscription_create'` does NOT identify the first real payment. A positive
amount does, whether or not a trial was involved.


=== THE LOGIC, IN ORDER ===

1. Skip immediately unless `inv.subscription` exists AND `(inv.amount_paid ?? 0) > 0`.
   A $0 trial invoice is not a payment.

2. Resolve the REFERRED organization id. Prefer `combined.organization_id` from
   the invoice/subscription metadata; fall back to looking up
   `stripe_subscriptions` by `stripe_subscription_id`. If neither resolves, log
   and skip — do not guess.

3. Load the `org_referrals` row where `referred_org_id` = that org. No row means
   this org was not referred: skip silently, this is the common case.

4. If the row's status is already 'rewarded' or 'rejected', skip. Nothing to do.

5. Compute `paidCount` as above and write it to `referred_paid_invoice_count`.
   Stamp `referred_first_payment_at` when it is still null and paidCount >= 1.

6. On the FIRST payment, record the card fingerprint and re-check eligibility.
   This is the first moment a card exists, which is why the self-referral card
   check lives here and not in claim-referral:

```ts
const fingerprint = (charge?.payment_method_details as any)?.card?.fingerprint ?? null;
```

   Write it to `referred_card_fingerprint`. Then load the REFERRER's fingerprint
   (the most recent non-null `referred_card_fingerprint` for any referral where
   that org was the referred party, or null if it has none) and call
   `rejectReason` from `_shared/referral-eligibility.ts` with both parties.

   If it returns a reason, set status 'rejected' with that
   `rejection_reason` and stop. Do NOT re-implement the comparison inline —
   two NULL fingerprints must not count as a match, and that rule is already
   pinned by tests in src/lib/referralEligibility.test.ts.

7. VEST. If `isVested(paidCount)` is true and status is still 'pending':
   set status 'qualified', stamp `referred_second_payment_at`, then invoke
   `grant-referral-reward` with the referral id. Use `isVested` from the shared
   module — do not write `>= 2` inline.

8. Wrap the whole referral block in its own try/catch that logs and swallows.
   A referral bug must never break receipt delivery or webhook acknowledgement
   to Stripe. Log with a `[referral]` prefix so it can be grepped.
