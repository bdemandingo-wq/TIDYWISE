=== THE MIGRATION ===

```sql
ALTER TABLE public.organizations
  ADD COLUMN IF NOT EXISTS onboarding_answers jsonb;

COMMENT ON COLUMN public.organizations.onboarding_answers IS
  'Onboarding qualifying answers, captured once at organization creation. Shape: {"teamSize":[],"bookingMethod":[],"biggestPain":[],"revenueGoal":[],"howHeard":[]} — every value is an array of option slugs because the questions are multi-select. Forward-looking only: NULL for organizations created before 2026-08-13, and deliberately never backfilled.';
```

That is the entire change.


=== WHY NOT: two things on this table that must stay exactly as they are ===

1. THE INSERT POLICY.

     CREATE POLICY "Users can create organizations"
     ON public.organizations FOR INSERT
     TO authenticated
     WITH CHECK (auth.uid() = owner_id);

   It is row-level and names no columns, so adding a column does not require
   touching it. Adding one nullable column changes nothing about who may insert.
   Leave it alone.

2. THE COLUMN-LEVEL UPDATE GRANT (migration 20260616202614).

     REVOKE UPDATE ON public.organizations FROM authenticated;
     GRANT UPDATE (name, slug, logo_url, updated_at) ON public.organizations TO authenticated;

   This is deliberate hardening: owners may edit display fields, but billing-state
   columns are off-limits to authenticated users. Do NOT add onboarding_answers to
   that grant list. The value is written once, inside the org-creation INSERT, and
   is never updated by a client afterwards. Adding it to the UPDATE grant would
   hand every logged-in owner a writable column for no reason.
