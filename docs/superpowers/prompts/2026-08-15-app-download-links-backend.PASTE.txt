=== PART 3 — public.user_sessions.platform ===

Run this migration:

  ALTER TABLE public.user_sessions
    ADD COLUMN IF NOT EXISTS platform text;

That is the whole migration. Specifically:

  - NO DEFAULT. Not 'web', not anything. A default would stamp a value onto
    rows nobody measured, and the entire point of this column is to be able to
    say truthfully who has opened the native app. NULL means "written before we
    tracked this," which is a real and different answer from "web".
  - NO BACKFILL for the same reason. Every existing row's platform is genuinely
    unknown and must stay that way.
  - NO CHECK constraint. The writer is Capacitor's getPlatform(), which returns
    'ios' | 'android' | 'web' today; a CHECK would turn a future platform string
    into a failed INSERT on a session-tracking write, which is a much worse
    outcome than an unexpected value in an analytics column.
  - NO index. The table is small and the query that will use this is a
    once-in-a-while admin question, not a hot path. Deliberate, not an oversight.
  - NO RLS change — see the Do NOT list above.

Nothing writes to this column yet. That is expected and correct: the frontend
change that populates it is blocked on this migration existing, because a
PostgREST insert naming an unknown column fails with 42703 and would silently
break session tracking for everyone. Migration first, frontend second.
