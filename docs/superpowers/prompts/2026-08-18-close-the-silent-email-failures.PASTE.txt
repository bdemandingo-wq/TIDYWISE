=== CLOSE THREE SILENT EMAIL FAILURES. ONE TURN. READ ALL OF IT FIRST. ===

Three edge functions send email through the Resend SDK and throw the result
away. The SDK returns { data, error } and does NOT throw on an API error, so a
403 lands in that discarded object, the "Email sent" line prints anyway, and in
one case a success row is written to automation_fire_log.

This is not theoretical. Regal Rest Cleaning has FIVE recorded weekly-summary
successes in automation_fire_log, and the Resend log shows 403s for
regalrestcleaning.com over the same period. The dashboard is reporting sends
that never happened.

THIS PASTE MAKES FAILURES VISIBLE. IT DOES NOT FIX WHY THEY FAIL.

Do NOT change any from-address. Do NOT change which API key is used. Do NOT
import _shared/email-sender-resolution.ts. The sender pairing is wrong in these
functions and that is being fixed separately, on purpose — closing the silence
first means the next failure shows up in the database instead of a provider log.
If you "helpfully" repoint a sender in this paste, the verification below cannot
tell the two changes apart.

  PART 1  weekly-business-report      check the result, and stop the fire log lying
  PART 2  notify-subscription-cancelled  check the result, stop returning success
  PART 3  weekly-payroll-summary      check the result

All verification is at the END.

THE FAILURE LOG. All three use the same existing RPC. Confirmed live signature:

  log_org_email_send_failure(
    _organization_id uuid,
    _method text,
    _fell_back_to text,
    _recipient text,
    _subject text,
    _error_message text
  )

It is SECURITY DEFINER and writes to public.org_email_send_failures, which is
where _shared/send-org-email.ts already logs. Use _method = 'resend' and
_fell_back_to = null, matching the 32 rows already in that table from the
resend path. Do not invent new values for those two columns.
