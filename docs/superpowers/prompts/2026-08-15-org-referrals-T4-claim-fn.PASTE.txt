=== WHY THE CLAIM IS A SERVER FUNCTION AND NOT A CLIENT INSERT ===

`public.organizations`' INSERT policy is `(auth.uid() = owner_id)` and does NOT
enumerate columns, so an authenticated user can already write any column on
their own org row. If attribution were client-writable a user could name any
referrer, mark themselves 'qualified', or grant themselves months.

So the four org_referral* tables carry SELECT policies only, and every write
goes through the service role. The client sends an org id and a code. These
functions decide everything else.

do not change `rejectReason`'s order of checks.

The properties its tests pin, so you can see what must not drift:

  - Two NULL card fingerprints are NOT a match. Both parties are unpaid at

  - A NULL plan_type is IN SCOPE. A brand-new org has not chosen a plan when
    the code is claimed.
  - isVested() is `>= 2`. Not 1.


=== STEP 2 of 3 — CREATE supabase/functions/claim-referral/index.ts ===

Behaviour, in order:

1. POST only. OPTIONS returns corsHeaders.

2. AUTHENTICATE THE CALLER AND CHECK THEY OWN THE ORG. This must not be
   skipped: the client supplies `organization_id`, so without it anyone could
   claim a referral on behalf of someone else's org.

   Read the Authorization header, resolve the user with an anon-key client
   (`auth.getUser(jwt)`), then confirm that user has an `org_memberships` row
   for the supplied organization_id with role 'owner'. Reject 403 otherwise.

   Do NOT add a config.toml entry for this function. With no entry it defaults
   to `verify_jwt = true`, which is what we want.

3. Normalise the code SERVER-SIDE. Do not trust the client's normalisation:
   uppercase, strip everything outside A-Z0-9, treat an empty result as a
   missing code (400). Must match `normalizeReferralCode` in
   src/lib/referralCode.ts.

4. Resolve the code to a referrer via `org_referral_codes`. No match -> record
   a rejected row (step 6) with reason 'invalid_code'.

5. Load both sides for the eligibility check:

   - referrer: `organizations.id, owner_id, plan_type` for the code's org
   - referred: `organizations.id, owner_id, plan_type` for the supplied org
   - cardFingerprint is NULL for both here and that is CORRECT. The card check
     runs in Task 6, at the referred org's first payment — the first moment a
     card exists. Pass null for both.

   Call `rejectReason(referrer, referred)` from the shared module. Do not
   re-implement its rules inline.

6. Insert exactly ONE row into `public.org_referrals`, accepted or rejected:

   - accepted:  status 'pending',  rejection_reason null
   - rejected:  status 'rejected', rejection_reason = whatever rejectReason
                returned (or 'invalid_code')

   Recording rejections is deliberate: it gives an audit trail, and because
   `org_referrals` has UNIQUE(referred_org_id) it stops an org retrying
   different codes until one sticks. If a legitimate claim is ever rejected in
   error, an admin deletes the row to allow a re-claim — say so in a comment so
   nobody later "fixes" it by skipping the insert.

7. Handle 23505 on `org_referrals_referred_once` as a NORMAL outcome:
   return `{ outcome: 'already_claimed' }` with status 200.

   The database also enforces `org_referrals_no_self`. If rejectReason somehow
   let a self-referral through, that CHECK raises 23514 — return
   `{ outcome: 'rejected', reason: 'self_referral_same_org' }`, not a 500.

8. Ensure a `public.org_referral_credits` row exists for the REFERRER
   (`insert ... on conflict (organization_id) do nothing`), so Task 7 has a
   ledger row. Zero months at this point.

9. Always return 200 with a JSON `outcome`:
   `claimed` | `already_claimed` | `rejected` | `no_code`

Service-role client for writes, anon client for `auth.getUser`.

THEN, immediately BEFORE `stripe.checkout.sessions.create` at ~line 229:

```ts
// The referred org's half of the programme. Only orgs that arrived through
// someone's referral link, and only on their first subscription.
//
// `org` is resolved inside the `if (user)` block above and is undefined for
// the anonymous checkout flow — see the KNOWN GAP note below. Capture the id
// into a variable in the outer scope so it is readable here.
let referralDiscount: { coupon: string }[] | undefined;
try {
  const couponId = Deno.env.get("REFERRED_FIRST_MONTH_COUPON");
  if (couponId && referredOrgId) {
    const { data: ref } = await accessAdmin
      .from("org_referrals")
      .select("id, status, referred_discount_applied_at")
      .eq("referred_org_id", referredOrgId)
      .in("status", ["pending", "qualified"])
      .maybeSingle();
    if (ref && !ref.referred_discount_applied_at) {
      referralDiscount = [{ coupon: couponId }];
    }
  }
} catch (e) {
  // Never block checkout over a discount lookup.
  console.error("[referral] discount lookup failed:", e);
}
```

Two things you must wire up for that to compile:

  - `referredOrgId` — declare it in the OUTER scope (`let referredOrgId: string
    | null = null;`) before the `if (user)` block, and assign `org?.id` inside
    it. Right now `org` is a const scoped to that block and is not visible at
    the session-creation site.
  - `accessAdmin` — same problem. It is created inside `if (user)`. Either
    hoist it or create a second service-role client at the discount lookup.
    Hoisting is cleaner; do not use the caller's anon client here, because
    org_referrals has SELECT policies scoped to the REFERRER and the referred
    org cannot read its own row.

Then add to the `stripe.checkout.sessions.create({...})` call:

Spread conditionally — passing `discounts: undefined` is not the same as

Confirm this function does not set `allow_promotion_codes`; I read it and it

Record that it was applied so it cannot be re-used on a second subscription:

=== KNOWN GAP — THE ANONYMOUS CHECKOUT FLOW ===

`create-subscription` supports checkout with NO logged-in user (it logs
`flow: user ? "authenticated" : "anonymous"`). In that path no organization
exists yet, so there is no org_referrals row and NO DISCOUNT CAN BE APPLIED.

This is accepted, not an oversight. The referral itself is not lost — the code
is still sitting in the browser's storage and claim-referral records it when
the user later completes onboarding, so the REFERRER still earns their month.
Only the referred org's 50% is missed, and only for people who subscribe before
creating their org.

DO NOT try to fix this by passing the referral code through checkout metadata.
That is a bigger change and I want to see the real frequency first.

REPORT how many of the last 20 checkout sessions took the anonymous path, if
you can tell from the logs. If it is common, this gap matters more than I think
and I will scope it as its own task.


=== THE TRIAL INTERACTION — READ THIS, IT IS THE RISKY PART ===

`create-subscription` sets `trial_period_days: 14` (line 227). That means the
FIRST invoice Stripe issues is $0, at subscription creation, before any charge.

I do not know with certainty whether a `duration: 'once'` coupon would be
consumed by that $0 invoice, leaving the customer with nothing when the real
charge lands 14 days later. That is exactly why the coupon above is
`repeating`/`duration_in_months: 1` — it is tied to a billing period rather
than to "the first invoice".

DO NOT take my word for it, and do not report success from seeing a coupon
attached to the subscription. The only thing that settles it is the FIRST
CHARGED invoice. Test it with a Stripe TEST CLOCK:

  3. Advance the clock past 14 days.
  4. Read the first invoice with `amount_due > 0`.

  EXPECT: 50% off. A $49 Basic plan invoices at $24.50.
