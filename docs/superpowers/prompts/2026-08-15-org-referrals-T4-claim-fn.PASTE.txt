=== WHY THIS IS A SERVER FUNCTION AND NOT A CLIENT INSERT ===

`public.organizations`' INSERT policy is `(auth.uid() = owner_id)` and does NOT
enumerate columns, so an authenticated user can already write any column on
their own org row. If attribution were client-writable a user could name any
referrer, mark themselves 'qualified', or grant themselves months.

So the four org_referral* tables carry SELECT policies only, and every write
goes through the service role here. The client sends an org id and a code. This
function decides everything else.

=== STEP 2 of 3 — CREATE supabase/functions/claim-referral/index.ts ===

Behaviour, in order:

1. POST only. OPTIONS returns corsHeaders.

2. AUTHENTICATE THE CALLER AND CHECK THEY OWN THE ORG. This is the part that
   must not be skipped: the client supplies `organization_id`, so without this
   anyone could claim a referral on behalf of someone else's org.

   Read the Authorization header, resolve the user with an anon-key client
   (`auth.getUser(jwt)`), then confirm that user has an `org_memberships` row
   for the supplied organization_id with role 'owner'. Reject 403 otherwise.

   Do NOT add a config.toml entry for this function. With no entry it defaults
   to `verify_jwt = true`, which is what we want — the gateway rejects an
   unauthenticated call before it reaches this code.

3. Normalise the code SERVER-SIDE. Do not trust the client's normalisation:
   uppercase, strip everything outside A-Z0-9, and treat an empty result as a
   missing code (400). This must match `normalizeReferralCode` in
   src/lib/referralCode.ts.

4. Resolve the code to a referrer via `org_referral_codes`. No match -> record
   a rejected row (see step 6) with reason 'invalid_code'.

5. Load both sides for the eligibility check:

   - referrer: `organizations.id, owner_id, plan_type` for the code's org
   - referred: `organizations.id, owner_id, plan_type` for the supplied org
   - cardFingerprint is NULL for both at this point and that is CORRECT. The
     card check runs later, in Task 6, at the referred org's first payment —
     which is the first moment a card exists. Pass null for both here.

   Call `rejectReason(referrer, referred)` from the shared module. Do not
   re-implement its rules inline.

6. Insert exactly ONE row into `public.org_referrals`, whether accepted or
   rejected:

   - accepted:  status 'pending',  rejection_reason null
   - rejected:  status 'rejected', rejection_reason = whatever rejectReason
                returned (or 'invalid_code')

   Recording rejections is deliberate. It gives an audit trail, and because
   `org_referrals` has UNIQUE(referred_org_id) it also stops an org retrying
   with a different code until one is accepted. If a legitimate claim is ever
   rejected in error, an admin deletes the row to allow a re-claim — say so in
   a comment so nobody later "fixes" it by skipping the insert.

7. Handle 23505 on `org_referrals_referred_once` as a NORMAL outcome, not an
   error: return `{ outcome: 'already_claimed' }` with status 200. The frontend
   retries are non-fatal and must not surface an error for this.

   Note the database also enforces `org_referrals_no_self`
   (referrer_org_id <> referred_org_id). If rejectReason somehow let a
   self-referral through, that CHECK raises 23514 — return
   `{ outcome: 'rejected', reason: 'self_referral_same_org' }` rather than a
   500. Two layers, deliberately.

8. Ensure a `public.org_referral_credits` row exists for the REFERRER
   (`insert ... on conflict (organization_id) do nothing`), so Task 7 has a
   ledger row to update. Zero months at this point.

9. Always return 200 with a JSON `outcome`. Never a 500 for a business
   rejection. The outcomes are:
   `claimed` | `already_claimed` | `rejected` | `no_code`

Use the service-role client for every write. Use `corsHeaders` from the shared
module the other functions use.
